- **feat(connectors): slice 557 — MDM event-driven (webhook) profile (Jamf + Intune).** Adds a `subscribe` profile to BOTH MDM connectors (slice 490 shipped them pull-only; this resolves its deferred P0-490-7): each connector's `profiles_supported` becomes **`[pull, subscribe]`**, named honestly — `subscribe` is **event-driven** vendor-webhook receipt, **NOT** "continuous monitoring" and not a relabeled poll. A new `webhook` subcommand on each connector runs a **source-side** receiver **inside the connector process** that receives the vendor's compliance-state-change deliveries, **verifies the per-vendor credential before any work**, maps the payload to the **same** `endpoint.device_posture.v1` record the pull profile emits (the slice-490 posture-summary field set, **unchanged**), and pushes it. **First external consumer of `connectors/shared/webhookrecv` (slice 656):** a thin shared adapter `connectors/mdm/mdmwebhook` wires the vendor `Verifier` + a per-vendor `PayloadParser` onto the shared `NewServer` (gosec-G112 timeouts) / `Serve(ctx)` graceful shutdown / `Handle(...)` verify-first skeleton (method→405, size→413, **verify-FIRST→401**) — **no second `http.Server` pattern stood up; the shared package was not modified.** **Per-vendor auth (the design crux — they DIFFER):** **Jamf** does NOT HMAC-sign webhook bodies, so a thin constant-time **shared-secret header** `Verifier` requires the operator-configured credential (`JAMF_WEBHOOK_SECRET`, header `X-Jamf-Webhook-Secret` overridable) before any record. **Intune / Microsoft Graph change notifications** need TWO things: (1) the **`validationToken` echo handshake** — when Graph creates/renews the subscription it sends a `validationToken` query param; the Intune adapter handles this **FIRST** (a `validationHandler` wrapping the receiver), responds **`200` text/plain with the token echoed**, and **builds NO record** (test-asserted); (2) a per-delivery **`clientState`** constant-time `Verifier` (`INTUNE_WEBHOOK_CLIENT_STATE`) — a mismatched or partially-forged batch is rejected **`401` before any record** (test-asserted). **Over-collection guard (P0-490-3, reused unchanged):** the parsers map into `devposture.RawDevice`, whose type system physically cannot hold device geolocation, an installed-app inventory, device contents, or owner contact PII — a webhook carrying those keys has nowhere to put them; a test pins the emitted payload to the posture-summary allow-list. The webhook payload is mapped directly (no re-read), so the connector never reads beyond the posture-summary and needs **no write/management MDM scope**. **Cross-profile dedup:** a webhook-emitted record and a later pull-emitted record for the same device in the same UTC hour derive the **same** idempotency key (the slice-490 `idem.DevicePostureKey`, unchanged), collapsing to one ledger row (test-asserted webhook-key == pull-key; Jamf prefers the numeric `jssID` so it matches the pull profile's REST `id`). **DoS bounding:** body size-bounded (256 KiB → `413`), verify-first, gosec-G112 timeouts; loopback-default bind (`127.0.0.1:8476`/`:8477`, TLS at a reverse proxy). **Log-injection hardened (b245 CodeQL):** every user-tainted log arg (device id + wrapped error) is `%q`-escaped. **Invariant #3 honored — push only; ZERO `internal/api/` / `migrations` / `proto` / `schemaregistry` changes:** the receivers stay source-side in the connectors; no migration, no new evidence kind, no `DefaultSeed` change. **Type: JUDGMENT** — the Jamf credential scheme, the Intune validation-handshake placement + clientState verifier, the map-payload-vs-re-read call, the dedup confirmation, and the receiver lifecycle/bind config are recorded in `docs/audit-log/557-mdm-webhook-decisions.md`.
