- **fix(audit): the original freeze of an audit period is immutable in the database (#3050).** Once `frozen_at`, `frozen_hash` or `frozen_by` is set on an `audit_periods` row, a trigger refuses any UPDATE that changes it, for every role, including a reset to NULL. On a frozen row the same trigger also fixes the fields the freeze hash covers (`id`, `tenant_id`, `period_start`, `period_end`, `framework_version_id`), so `ReplayHash` keeps reproducing `frozen_hash`; `name` stays editable. `populations.frozen_at` is write-once too. A third trigger keeps `audit_period_freeze_revisions` an unbroken chain: revision N is accepted only on a frozen period whose latest revision is N - 1, with `previous_hash` equal to that revision's hash. The first freeze, inserts of already-frozen rows (demo seed, fixtures) and adding a revision through a historical import all still work. Migration `20261307000000_audit_period_freeze_immutable` (with down file). **Upgrade note:** a frozen period can no longer be reopened by a direct UPDATE; the owner-only recovery, and why it must never be used on a period with freeze revisions, is in `docs/runbooks/audit-period-reopen.md`.
