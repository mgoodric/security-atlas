- **feat(connectors): slice 521 — Azure Key-Vault access-policy / RBAC evidence.** Adds a fifth evidence kind to the Azure connector (slices 486 / 519 / 520): `azure.keyvault_access_config.v1`. A new `connectors/azure/internal/keyvault` collector reads, read-only via Azure Resource Manager (ARM **Reader** role — **no** new Azure scope, P0-521-3), each Key Vault's **management-plane** posture: the access model (legacy access policies vs Azure RBAC authorization), purge-protection + soft-delete state, public-network-access posture, network-ACL default action, and the principals entitled to the vault (legacy access-policy entries with their granted keys/secrets/certificates permission **verbs**, plus the RBAC-mode flag). **Over-collection guard (the slice-520 gold standard, load-bearing here because Key Vault holds secrets):** the connector reads the ARM management plane **only** (vault list + access policies) and **never** the Key-Vault **data plane** (`vault.azure.net` secret/key/certificate get); it requires **no** Key-Vault data-plane role (`Key Vault Secrets User`, `Key Vault Crypto User`, etc. — the over-privilege trap, P0-521-1) and the collector struct has **no field** for any secret/key/certificate value (P0-521-2). A structural reflection test fails the build if any struct field name hints at secret material; the integration over-collection test descends into the access-entry list applying a per-kind allow-list. Schema `azure.keyvault_access_config/1.0.0.json` carries `x-default-scf-anchors` `["IAC-21", "CRY-09"]` (privileged-account-management + cryptographic-key-management) and is wired into `schemaregistry.DefaultSeed` (drift bijection passes).
