- **fix(deploy): slice 473 — self-host stack now applies migrations on EVERY bring-up, fail-closed, so a Watchtower binary update can never serve against a stale schema.** Confirmed production incident (2026-06-05): the maintainer's atlas-edge box silently fell 3 migrations behind after an image update — Watchtower auto-updates the `atlas[-edge]` BINARY (it carries the watchtower-enable label) but NOT the `atlas-bootstrap[-edge]` one-shot (no label, `restart:"no"`), and the backend `depends_on` it with `condition: service_started` rather than `service_completed_successfully`. The newer binary ran against the older schema; the demo-seed button then failed with a **masked HTTP 500** (the `me_audit_log_action_check` CHECK rejected the `demo_seed` action value the un-applied `20260525000000_demo_seed_button_meta_audit` migration would have added), surfacing hours later as "action failed" rather than at deploy time. **Fix:** the migrate step is split out of the first-boot bootstrap into a dedicated **always-run** `atlas-migrate[-edge]` service (`deploy/docker/bootstrap/migrate.sh`) that applies any `migrations/sql/*.sql` not yet in the `schema_migrations` ledger — as `atlas_migrate` (`BYPASSRLS`, no superuser, no down-migrations), one transaction per file — on every `docker compose up`. It is **idempotent** (an already-current DB applies nothing and logs `schema current`; no re-seed) and **fail-closed** (a failing migration exits non-zero naming the file, and the `atlas[-edge]` backend — now gated on `atlas-migrate[-edge]` via `service_completed_successfully` — does NOT serve a partial schema). `atlas-migrate[-edge]` carries the watchtower-enable label so it advances in lockstep with the binary; `atlas-bootstrap[-edge]` keeps `service_started` to preserve the slice-065 deadlock avoidance (its control-upload phase blocks on atlas `/health`) and now seeds only a fully-migrated schema. Applied to BOTH `docker-compose.yml` (bundled `build:`) and `docker-compose.edge.yml` (pulled `:edge`). **Proof (AC-7):** a new `migrate` mode in `deploy/docker/test-self-host-bundle.sh` (CI self-host-bundle matrix leg, mirroring slice 470's `proxy` leg) reproduces the incident — bring up at set N, write a new sentinel migration, re-run `atlas-migrate`, assert the migration applied (ledger N→N+1), the force-recreated backend serves a CURRENT schema (the gate held), and a second run is an idempotent no-reseed `schema current` no-op; run green end-to-end. `docs/SELF_HOSTING.md` + the upgrade runbook (`docs-site/docs/upgrade.md`) document the migrate-on-upgrade behavior + fail-closed contract and reconcile the slice-464 migrate-command drift (the binary has no `migrate` subcommand). **Type: JUDGMENT.** Decisions log: `docs/audit-log/473-migrate-on-upgrade-decisions.md`.
