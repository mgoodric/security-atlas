- **feat(connectors): slice 489 — PagerDuty connector (incident-response evidence): on-call coverage + bounded-window incident summaries.** A new first-class peer connector — `connectors/pagerduty/` — answers the recurring SOC 2 CC7.3 / CC7.4 / CC7.5 auditor demand ("show your on-call schedule and your incident history") and the slice-372 IR plan, today a manual upload. It follows the locked slice-004 / 486 / 487 / 488 connector pattern verbatim (register-per-run, stable `actor_id`, hour-truncated `observed_at`, scope minimums, vendor-native read-only auth) and emits **two evidence kinds**: `pagerduty.oncall_coverage.v1` (escalation policy, its tiers, and the on-call IDENTITY — opaque id + display name — needed to prove coverage; read-only PagerDuty REST `GET /escalation_policies`) and `pagerduty.incident_summary.v1` (incident id / number / urgency / status / service / created+resolved timestamps over a bounded look-back window; read-only `GET /incidents?since=&until=`). Each record is pushed to the platform's single `IngestEvidence` / `Push` API with a sha256 content-hash and stable optional fields — **no platform-side wire change** (invariant #3, P0-489-1); the connector registers `profiles_supported=[pull]` and names its interval honestly (operator-scheduled, recommended 24h — **not** "continuous monitoring", P0-489-6). **The load-bearing over-collection guard (P0-489-3 / threat-model I):** the connector collects coverage facts + incident-SUMMARY metadata only — on-call identity (id + display name) and incident id/urgency/status/service/timestamps — and **never** a responder's personal phone number or personal email, the incident's free-text title/body/notes (which can embed customer data), or postmortem text. The boundary is enforced **by construction** (the `oncall.RawTarget` type has no phone/email field and the connector never fetches `/users`; the `incidents.RawIncident` type has no title/body/notes field; the clients decode only the listed fields, so unwanted PII / free-text never enters memory) plus tests: a record-shape test asserts no PII-shaped or free-text substring reaches an emitted payload (AC-10), and another asserts the PagerDuty token is never logged (AC-11). The read-only REST API token is read only from the environment (never a CLI flag), redacted on every credential format path, and never placed into a record (P0-489-4); the connector requires a **read-only least-privilege token only**, surfaced by the `permissions` subcommand and warned against write/admin (P0-489-2). It is **OSS, in-tree, read-only API** (P0-489-5) and faked in tests (no live PagerDuty in CI — a thin read-only HTTP client `pdhttp`, no heavy vendor SDK; the in-package bufconn integration test exercises the full collect → build → `Push` → receipt round-trip for both kinds and same-hour idempotency). Two evidence-kind JSON Schemas land in the schema-registry tree with `x-default-scf-anchors` set (`IRO-04`/`IRO-07` for coverage, `IRO-02`/`IRO-09` for incidents — flagged for maintainer recheck per OQ #9) and are registered in `DefaultSeed`; no migration. The incident look-back window defaults to 90 days (`--lookback-days`, bounded — threat-model D). Postmortem/retrospective evidence, responder-performance metrics, and an event-driven webhook profile are filed as follow-on slices 538–540 (P0-489-7). **Type: JUDGMENT** — the two evidence-kind shapes, the on-call-identity-vs-PII boundary, the look-back window, the scope minimums, and the `x-default-scf-anchors` recorded with confidence + detection-tier in `docs/audit-log/489-pagerduty-connector-decisions.md`.
