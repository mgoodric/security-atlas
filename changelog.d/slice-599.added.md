- **feat(oscal): slice 599 — OSCAL resolved-chain provenance read API.** Slice 578 records the resolved import chain as provenance in the `imported_catalog_audit_log.detail` JSON of the `profile_imported` success row — a `chain` array of `{role, sha256, bytes}` entries (entry profile + intermediate profiles + catalogs) plus a `chain_depth` count — but that provenance was WRITTEN with no read surface: it was only queryable by reading the raw audit-log JSON. This slice adds the read path so an operator or auditor can prove, for an imported profile baseline, the exact ordered chain of documents (and their sha256 hashes) that resolved it — the "diligence the diligence tool" provenance story for chained imports. **Route:** `GET /v1/oscal/imported-profiles/{id}/provenance` returns `{baseline_id, profile_title, source_label, oscal_version, source_sha256, imported_at, chain_depth, chain[]}` where each chain entry is `{role, sha256, bytes}` in document order (AC-1). A single-level slice-511 import returns its two-element `[entry-profile, catalog]` chain without special-casing (AC-2). **Tenant-scoped (AC-3):** the read rides RLS plus an explicit `tenant_id` predicate on a new sqlc query (`GetProfileImportProvenance`) that joins `imported_catalogs` (confirming `kind = 'profile'`) to its `profile_imported` audit row; a cross-tenant or unknown id returns 404 (the integration suite asserts tenant A cannot read tenant B's provenance, and that tenant B can read its own). The read is a pure SELECT over the existing append-only audit-log table — **no migration, no write path** (constitutional invariant #2) — and **never touches the compliance-trestle bridge** (the provenance is already persisted in Postgres), so the read path is testable with seeded DB rows alone and runs in CI without the Python bridge. New read package `internal/api/oscalprovenance` (Store + Handler mirroring the slice-064 `controldetail` read pattern: per-request tenant-GUC transaction, handler-level defense-in-depth role guard admitting admin + grc_engineer + control_owner — the OPA middleware is the primary gate). Enrolled in `scripts/integration-shards.txt` (Leg A) with a 88% coverage floor. **Type: code.** Parent: slice 578 (the write).
