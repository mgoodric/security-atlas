- **feat(connectors): slice 615 — Azure Key-Vault RBAC role-assignment enumeration.** Closes the slice-521 gap (521 D3/D5): for a Key Vault in **Azure RBAC authorization** mode (`enableRbacAuthorization=true`) the `connectors/azure/internal/keyvault` collector now issues a SECOND read-only ARM read — `Microsoft.Authorization/roleAssignments` scoped to the vault resource id — and merges each into the existing `access_entries` list as a `principal_type=rbac_role_assignment` entry (principal object id + resolved role definition **name**, e.g. `Key Vault Reader`, `Key Vault Secrets User`). This makes the least-privilege read **symmetric** across both vault access models (legacy access-policy vaults were already enumerated in full), completing the IAC-21 privileged-account-management signal for RBAC vaults. **Read shape (JUDGMENT, D1):** the second read lives inside `Client.ListVaults` so the `keyvault.API` seam and the `Inspect` collector are byte-for-byte unchanged — an RBAC vault's principals come from roleAssignments exactly as a legacy vault's come from `accessPolicies`; a legacy vault triggers NO second read. Role **names** are resolved via a bounded, per-run-cached `roleDefinitions` lookup (Reader can read role definitions); a failed/empty lookup falls back to the bare role-definition guid so the evidence still names the role unambiguously. **NO schema change (AC-2):** `azure.keyvault_access_config.v1` already carries the discriminated `access_entries[].principal_type` enum (`access_policy | rbac_role_assignment`) + `role_name` (the drift bijection passes unchanged). **Over-collection guard (the slice-521 structural pin, extended to the new path, D2):** roleAssignments + roleDefinitions are wholly **management-plane** METADATA (principal id + role name) — the `keyvault.AccessEntry` struct still has **no field** capable of holding a secret/key/certificate value, so the RBAC path cannot over-collect by construction; the reflection structural test covers the type and a new `TestRBACRoleAssignment_MetadataOnly_PinsNewPath` pins the path. The connector reads ARM **Reader** only (P0-615-3) and NEVER the Key-Vault data plane (`vault.azure.net`, P0-615-2) — the client test asserts no roleAssignments call is ever issued for a legacy vault and the data plane is never touched. **DoS guard (threat-model D):** the per-vault read is a single bounded page truncated to `maxRoleAssignmentsPerVault` (200), the run-wide total is capped at `maxRoleAssignmentsPerRun` (2000), and distinct role-definition lookups are capped at `maxRoleDefinitionLookupsPerRun` (100); a per-vault read error marks that vault INCONCLUSIVE (fail-soft) without failing the run. Cursor pagination for a huge estate is a documented follow-on (spillover slice 623), NOT implemented here. Push-only (invariant #3); `profiles_supported=[pull]`; stable `actor_id` `connector:azure:keyvault@<version>`; hour-truncated `observed_at`; the `keyvault` coverage floor (90) holds (measured 91.5%). **Type: JUDGMENT** — the read-shape choice, the role-name-resolution scope-minimum, and the over-collection-guard mechanism recorded with detection-tier in `docs/audit-log/615-azure-keyvault-rbac-decisions.md`.
