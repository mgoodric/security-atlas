- **feat(connectors): slice 488 — Datadog + Grafana monitoring connectors, the monitoring/alerting evidence family.** Two new first-class peer connectors — `connectors/datadog/` and `connectors/grafana/` — answer the recurring SOC 2 CC7.2 ("the entity monitors system components") evidence demand ("prove monitors/alerts are configured and route to on-call"), today a manual screenshot upload. Both follow the locked slice-004 / 486 / 487 connector pattern verbatim (register-per-run, stable `actor_id`, hour-truncated `observed_at`, scope minimums, vendor-native read-only auth) and emit **one shared evidence kind** — `monitoring.alert_config.v1` — because the two vendors' alert-configuration field set is identical at the config-inventory altitude (a `source_vendor` discriminator preserves provenance; the shared shape is built once in `connectors/monitoring/monrecord`). **Datadog** collects monitor inventory (name, type, enabled state, notification-target handles parsed from the monitor message) via the read-only Datadog API (`GET /api/v1/monitor`, `monitors_read` scope). **Grafana** collects alert-rule + notification-policy inventory (rule title, type, enabled/not-paused state, folder, contact-point name) via the read-only Grafana provisioning API (Viewer-role service-account token). Each record is pushed to the platform's single `IngestEvidence` / `Push` API with a sha256 content-hash and stable optional fields — **no platform-side wire change** (invariant #3, P0-488-1); each registers `profiles_supported=[pull]` and names its interval honestly (operator-scheduled, recommended 24h — **not** "continuous monitoring", P0-488-6). **The load-bearing over-collection guard (P0-488-3 / threat-model I):** both connectors collect monitor/alert + routing-target **metadata only** — rule name, type, enabled state, and the notification-target **handle / channel / contact-point NAME** — and never the secret webhook URL, integration tokens, recipient email addresses (PII), dashboard JSON, metric time-series, or log results. The guard is enforced by construction (the shared `alertcfg.Target` type has no secret field; the Grafana `ContactPoint` struct has no `settings` field, and the Datadog client never decodes the monitor `query` / `options` blob — so secrets never enter memory as connector data) plus tests: the Datadog message parser **drops `@user@example.com` email-recipient mentions**, and a record-shape test asserts no secret URL / token / recipient PII reaches an emitted payload. Source keys/tokens are read only from the environment (never a CLI flag), redacted on every credential format path, and never logged or placed into a record (P0-488-4); both auths require **read-only least-privilege scopes only** (Datadog `monitors_read`, Grafana `Viewer`), surfaced by each connector's `permissions` subcommand (P0-488-2). Both are **OSS, in-tree, read-only API** (P0-488-5) and faked in tests (no live Datadog/Grafana in CI — thin read-only HTTP clients, no heavy vendor SDKs). The shared `monitoring.alert_config.v1` JSON Schema lands in the schema-registry tree with `x-default-scf-anchors=[MON-01]` (Continuous Monitoring) and is registered in `DefaultSeed`; no migration. Datadog Cloud-SIEM rule evidence, Grafana SAML/RBAC config evidence, and an alert-firing-history event-driven profile are filed as follow-on slices 533–535 (P0-488-7). **Type: JUDGMENT** — the shared-vs-split evidence-kind decision, the `x-default-scf-anchors` choice, and the per-connector scope minimums are recorded with confidence + detection-tier in `docs/audit-log/488-monitoring-connectors-decisions.md`.
