- **feat(auth): slice 478 — super-admin user↔tenant↔role assignment API (incl. self-assignment).** Closes the deferred slice-060.5 backend gap: there was no admin API to manage who belongs to which tenant. A user's tenant membership is a `users` row keyed by `(idp_issuer, idp_subject)` per tenant (read by the slice-192 resolver's `enumerateMemberships`); capabilities come from `user_roles` (slice-035 enum). The slice-062 `adminusers` package only exposed a within-tenant list/get/patch-roles surface. This slice extends it with the **cross-tenant super-admin** surface — a super-admin can now list users across every tenant, **assign** a user identity to a tenant with role(s), **revoke**, and crucially **self-assign** (add themselves to a tenant they super-administer but are not a member of, so the membership-bounded switcher [P0-192-5] surfaces it after re-auth). **Routes:** `GET /v1/admin/users` now dispatches super-admins to a paginated cross-tenant view (keyset cursor over `(tenant_id, id)`, bounded — no unbounded scan) and everyone else to the unchanged within-tenant list; `POST /v1/admin/users/assign` and `POST /v1/admin/users/revoke` are new. **Authority tiers (P0-478-1):** cross-tenant writes require the verified `atlas:super_admin` JWT claim (enforced server-side by `requireSuperAdmin`, second-legged by the OPA `admin.rego`/default-deny gate — P0-478-4); within-tenant writes are allowed for a tenant-admin and run under RLS; a tenant-admin naming a foreign tenant is denied 403 (tested). Cross-tenant writes use the BYPASSRLS auth pool (the target tenant ≠ the actor's GUC), mirroring `admintenants.Create`; assign is atomic (membership + roles in one tx) and idempotent. **THE load-bearing call — local-auth identity (P0-478-2, slice 478 D1):** local operators have an empty `(idp_issuer, idp_subject)` tuple; copying it into a second-tenant membership would make the resolver over-match _every_ local user across _all_ tenants (the slice-476 hazard). Resolved by minting a **stable synthetic per-user key** (`idp_issuer='urn:atlas:local'`, `idp_subject=<origin users.id>`) written to both the new membership row and (backfill) the origin row — non-empty so the resolver surfaces it, unique per local user so it can never over-match; local login is unchanged (the synthetic issuer is never used for token exchange). The non-over-match is proven by an integration test that assigns two distinct local users to a shared tenant and asserts each resolves to exactly its own two memberships. **Audit (AC-7):** every assign/revoke writes a tenant-scoped `me_audit_log` row (surfaced by the slice-124 aggregator) plus, on the super-admin cross-tenant path, a platform-global `super_admin_audit_log` row + a slice-126 sink fanout; two new action values (`user_tenant_assign`, `user_tenant_revoke`) extend both CHECK constraints (`migrations/sql/20260607010000_user_tenant_assignment_audit.sql`, reversible). **Scope:** backend API + membership/role write + the `available_tenants` refresh path only; NO UI (slice 479), NO invitation/email/SCIM/password flows, NO auto-switch of the actor's tenant (P0-478-5), NO change to OPA role semantics. The slice-192 resolver/switcher is untouched (P0-478-3). **Tests:** pure-Go unit (`helpers_test.go`: assign validation, cursor round-trip, limit clamp, synthetic-key invariant) + a real-Postgres integration suite (cross-tenant assign + idempotency + audit, self-assign reachable in the real resolver end-to-end, local-auth non-over-match, the authz DENY cases, within-tenant RLS-correct write, cross-tenant-vs-scoped list). Neutral `test-*` fixtures only (P0-478-6). **Type: JUDGMENT** — local-auth identity mechanism, the two-tier authority model, revoke membership semantics, and the audit dual-write recorded in `docs/audit-log/478-user-tenant-assignment-decisions.md`. Unblocks slice 479 (the admin user-management UI) and subsumes the mechanism slice 476 needed (demo reachability via self-assign).
