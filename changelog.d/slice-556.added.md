- **feat(connectors): slice 556 — MDM configuration-profile detail evidence (Jamf + Intune).** Slices 490 (posture summary) and 555 (software inventory) reported WHETHER a managed device is compliant and WHAT software it runs; this slice adds a third, scoped sibling kind `endpoint.config_profile.v1` reporting WHICH configuration / compliance profiles are deployed to a managed device and what compliance-relevant settings they enforce — evidence for configuration-management controls (auditors increasingly ask for the baseline itself: "show the screen-lock policy that is enforced", "show the disk-encryption configuration profile"), `x-default-scf-anchors = [CFG-02, CFG-04]` (Secure Baseline Configurations / Configuration Change Control). It is a SEPARATE kind, not an extension of posture or software-inventory, because it answers a different control question at a finer grain than the posture verdict. **THE LOAD-BEARING SECRET-REDACTION BOUNDARY (P0-556 / threat-model I): configuration profiles routinely embed SECRETS — Wi-Fi PSKs, VPN shared secrets, certificate private keys, API tokens, SCEP challenges, and arbitrary password / `<data>` / `PayloadContent` payload values — and NONE of these ever enters an evidence record.** Enforcement is structural at THREE layers (the slice-490/555 gold standard), so a leak is a compile error, a not-requested field, AND a dropped key: (1) the shared `cfgprofile.Setting` / `RawSetting` + the per-vendor `RawConfigSetting` Go types carry only an allow-listed `key` + a non-secret summary `value` — there is NO field anywhere in the type graph for a raw payload blob, a password, a private key, or a shared secret, so a leak would be a compile error; (2) the vendor clients request profile METADATA only at the API boundary — Jamf asks for the `GENERAL + CONFIGURATION_PROFILES` inventory sections (never `USER_AND_LOCATION` / GPS `location` / `APPLICATIONS`, and the section returns no raw payload blob), Intune `$select`s the device `id` and `$expand`s `deviceConfigurationStates($select=id,displayName,state)` (never `deviceName` / `userPrincipalName` / the raw setting payload), both read-only GETs; (3) the settings allow-list (`cfgprofile.AllowedSettingKeys`: `passcode_required`, `disk_encryption_enforced`, `firewall_enabled`, `screen_lock_enforced`, …) is the ONLY set of keys that may enter a record, with a belt-and-braces deny-list (`IsBannedSettingKey` — `password` / `secret` / `psk` / `privatekey` / `token` / `challenge` / `payloadcontent` / `certificate` / `data` / `pin` / …) re-applied at BOTH the normalizer and the record builder so even a hand-built `Device` cannot smuggle a secret. The required secret-redaction test `TestBuild_PayloadCarriesProfileFieldsOnly_NoSecrets` hand-builds a profile carrying `wifi_password` / `vpn_shared_secret` / `certificate_private_key` / `PayloadContent` and asserts only allow-listed keys reach the payload AND a recursive walk over the whole record finds none of the secret VALUES; per-connector client tests assert the request never asks for the banned sections/props. A new shared `connectors/mdm/{cfgprofile,cfgrecord}` package family mirrors the slice-490 `{devposture,devrecord}` / slice-555 `{swinventory,swrecord}` split (one normalizer + one record builder across both vendors), the `idem` package gains a kind-namespaced `ConfigProfileKey` (so a device's posture + software + config-profile records never collide on the same key for a given device+hour — proven by `TestConfigProfileKey_NamespacedFromSiblings`), and each connector gains a `run-config-profiles` subcommand (pull profile; honest 24h operator-scheduled cadence — NOT continuous monitoring). The per-device profile list is stable-sorted and bounded (`MaxProfilesPerDevice = 200`, `MaxSettingsPerProfile = 64`). Read-only credential is **identical** to `run` (no new MDM scope; no write/management permission — the remote-wipe guard from slice 490 is unchanged); records are `service` + required `--environment` scoped; `Result = INCONCLUSIVE` (the platform evaluator owns the pass/fail). Wired into `schemaregistry.DefaultSeed()` + the bundled JSON Schema (`endpoint.config_profile/1.0.0.json`); the schema-drift bijection passes. New floored packages `connectors/mdm/cfgprofile` (94) + `connectors/mdm/cfgrecord` (96). No migration — evidence flows through the slice-013 ledger. **v0 emits per-profile METADATA only** (the Jamf CONFIGURATION_PROFILES section + Intune deviceConfigurationStates are metadata-only; the `settings[]` array is wired end-to-end through the allow-list guard and tested via fixtures but empty for both vendors at v0) — per-setting enrichment through the SAME allow-list is spillover slice 595. **Type: JUDGMENT** — the separate-sibling-kind call, the per-device-roll-up shape, the configuration-profile field set, the SCF anchors, and THE secret-redaction allow-list / structural boundary recorded with detection-tier in `docs/audit-log/556-mdm-config-profile-decisions.md`.
