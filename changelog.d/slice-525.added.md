- **feat(connectors): slice 525 — Kubernetes Secret-inventory (metadata-only) evidence.** Adds a fifth evidence kind `k8s.secret_inventory.v1` to the Kubernetes connector (slice 487) — and is the **one deliberate exception** to the connector family's no-Secrets rule. Slice 487 withheld all Secret access (the base ClusterRole does not grant `secrets`); this slice adds, **OPT-IN** (`run --collect-secret-inventory`, off by default), a Secret **metadata** inventory: per Secret the `type` (`Opaque` / `kubernetes.io/tls` / `kubernetes.io/service-account-token` / ...), namespace, name, creation timestamp + derived `age_days`, `key_count`, and the **NAMES** of the keys under `.data` (the map keys, e.g. `tls.crt` / `tls.key` / `token`). The auditable question is "how many TLS secrets / SA tokens exist, where, and how old" (rotation + sprawl signals), never the contents. A new `connectors/k8s/internal/secretmeta` collector mirrors the slice-487/523/524 pattern (`secretmeta.Collect` ↔ `pss.Assess`, `secretmeta.Client` ↔ `pss.Client` over the shared slice-621 `k8slist.ListAll` paginating reader, `idem.SecretInventoryKey`, `buildSecretMetaRecord`). **JUDGMENT — THE load-bearing metadata-only guard (Information Disclosure is the PRIMARY threat because the ClusterRole now reaches `secrets`):** a Secret VALUE (`.data` / `.stringData`, raw or base64) physically **cannot** enter a record. Enforced **structurally**, not procedurally: (1) the `RawSecret` / `Inventory` structs have no value field (`KeyNames []string` holds the `.data` MAP KEYS only); (2) the client decode models `.data` as `map[string]json.RawMessage` and `reduce()` reads only the map KEYS — the base64 values are never decoded, never copied into a record-bound field, and `.stringData` is not modeled at all (the json decoder discards it); (3) a reflection guard (`TestStruct_MetadataOnly_NoValueBearingFields`) FAILS THE BUILD if any field name hints at a value / data / content / payload surface (`KeyNames` allow-listed — names, not values); (4) `TestReduce_DropsSecretValues` + `TestClient_NoSecretValueReachesRecord` feed a fixture Secret with REAL `.data` (base64), `.stringData` (plaintext), and a secret-bearing annotation, serialize the whole record, and assert NONE of those markers — base64, the base64-DECODED form, or the plaintext — appears anywhere. **JUDGMENT — the ClusterRole grant (AC-4):** `k8sauth.SecretsRule()` adds EXACTLY one rule — core `secrets` verbs `get,list` — and `SecretInventoryClusterRole()` = base `DocumentedClusterRole()` + that one rule. The base role is UNCHANGED and still excludes `secrets` (the existing least-privilege test still asserts it); two new tests pin that the inventory role adds exactly the one secrets get/list rule, introduces no wildcard, and grants no write verb. The `permissions --secret-inventory` subcommand prints the role WITH the grant (loudly documented as the one access the base connector withheld); the default `permissions` output still withholds it. **JUDGMENT — anchors:** `x-default-scf-anchors=[CRY-01, CRY-09]`. The spec's candidate `IAC-22` is **absent** from the bundled SCF catalog (a dangling anchor fails the slice-068 drift guard); `CRY-01` ("Use of Cryptographic Controls") + `CRY-09` ("Cryptographic Key Management" — the closest real anchor for the secret-material rotation/sprawl signal) are both present and resolve. `--secret-control` defaults to `scf:CRY-01`. **JUDGMENT — opt-in (D5):** unlike the other four kinds (on by default, individually skippable), this kind is off by default and individually enabled — collecting Secret objects is an explicit, auditable operator decision that lines up 1:1 with the explicit ClusterRole change. **Anti-criteria (P0):** push only — no platform-side wire change (invariant #3); metadata only — no Secret values (the structural guard); exactly `secrets` get,list — no write verb, no wildcard; the `pull` profile is named honestly (NOT continuous monitoring). The record is **descriptive** (`INCONCLUSIVE`) — an inventory signal, not a verdict; the evaluator owns any rotation policy call. sha256 content-hash per record; hour-truncated `observed_at`; register-per-run; stable `actor_id=connector:k8s:secretmeta@<version>`; per-Secret `namespace` scope dimension. The schema (`k8s.secret_inventory/1.0.0.json`, `additionalProperties:false`, NO value property) is registered in `DefaultSeed` (the slice-068 drift bijection passes). A per-run cap (`secretmeta.maxSecrets=20000`) bounds the inventory. Neutral fixtures only (obviously-fake `base64("test-secret-value-should-be-dropped")` + plaintext markers; no vendor-shaped literals). New `connectors/k8s/internal/secretmeta` coverage floor (96; measured 98.0%). No migration, no new tenant-scoped table, no RLS change. **Type: JUDGMENT** — the field shape, the structural metadata-only guard, the single-rule ClusterRole grant, the anchor choice (CRY-01/CRY-09 vs the dangling IAC-22), the opt-in decision, and detection-tier are recorded in `docs/audit-log/525-k8s-secret-inventory-decisions.md`.
