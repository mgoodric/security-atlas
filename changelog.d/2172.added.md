- **feat(modules): module access for each member (#2172).** An admin narrows where a member can work from Admin › Users: each member's row has a module-access control next to their role, set to "All modules" (a wildcard that includes modules switched on later, and the default for every new and existing member) or an explicit set of optional modules. It applies to `grc_engineer`, `control_owner` and `viewer`; admins always have every switched-on module, auditors are unaffected, and an admin cannot narrow their own access. A switched-on module outside a member's access answers `403` naming the module (`{"error":"You don't have access to …","module":"…","module_name":"…"}`) from one step in the authorization chain, after the module gate (a switched-off module still answers `404` with the switched-off marker) and before the OPA role decision. `GET /v1/me/modules` reports `no_access` for those modules, the sidebar leaves them out, and opening one shows "You don't have access to <module>. Ask an administrator." Backed by `PUT /v1/admin/users/{id}/module-access` (tenant admin; the member must belong to the caller's tenant) and `module_access` on the `GET /v1/admin/users` rows. Every change is logged before and after in the same transaction in an append-only access audit log, which shows in Activity and the unified audit log as kind `module_access` (migration `20261230000000`).
