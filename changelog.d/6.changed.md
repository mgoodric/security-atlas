- **fix(oscal): slice 659 — OSCAL component-definitions list 500: reproduce + diagnose (migration-lag, not a code bug).** The Vendor Claims page (`/oscal/component-definitions`) returned **HTTP 500** in the EMPTY/default tenant on an edge deploy. A DIAGNOSE-THEN-DECIDE reproduce against a **fully-migrated** Postgres (all 83 `migrations/sql/*.sql` applied) proved the platform code is **correct**: an empty tenant returns `200 {"component_definitions":[],"count":0}`, a populated tenant returns the rows, and cross-tenant reads stay RLS-isolated (invariant #6). The edge 500 is **migration-lag** — the edge `imported_catalogs` table is missing the `kind`/`profile_title` columns added by `migrations/sql/20260608000000_oscal_imported_profiles.sql` (slice 511); sqlc bakes `kind` into the generated `ListImportedComponentDefinitions` query (SELECT list + `WHERE kind = 'component_definition'`), so Postgres rejects it at **parse time** (`column "kind" does not exist`) **regardless of row count**, which is why even the empty tenant 500'd. **No code/query/migration change** (`git diff --stat origin/main...HEAD -- proto/` and `-- migrations/` both empty; no sqlc regen). This slice adds the regression guard `TestList_EmptyTenantReturns200EmptyList` (`internal/api/oscalcomponents/integration_test.go`, `//go:build integration`) that locks in "empty migrated tenant → 200 + empty list" so a future query/migration mismatch is caught in CI, not a deploy. The 500 path uses `httperr.WriteInternal` (slice 367) — verified the client body is a bare `{"error":"internal error","request_id":...}` with no SQL/column/stack leak. The operational fix (apply the missing migration on the edge box + read the `atlas-migrate-edge` logs to find why migrate-on-bringup skipped it) needs maintainer edge access and is filed as deploy-note spillover slice 683 (`not-ready`, BLOCKED on edge-log access). **Type: JUDGMENT** — decisions log `docs/audit-log/659-oscal-component-definitions-500-decisions.md`.
