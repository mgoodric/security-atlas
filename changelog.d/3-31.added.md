- **feat(connectors): slice 490 — Jamf + Intune MDM connectors (managed-device endpoint posture).** Two new first-class peer connectors — `connectors/jamf/` and `connectors/intune/` — answer the recurring SOC 2 CC6.7 / CC6.8 and ISO A.8 auditor demand ("prove laptops are disk-encrypted, have a screen-lock policy, and are managed"), today a manual MDM export. Both follow the locked slice-004 / 486 / 487 / 488 / 489 connector pattern verbatim (register-per-run, stable `actor_id`, hour-truncated `observed_at`, scope minimums, vendor-native read-only auth) and emit **one shared evidence kind** — `endpoint.device_posture.v1` — because the two MDMs' device-posture field set is identical at the posture-summary altitude (a `source_mdm` discriminator preserves provenance; the shape is normalized once in `connectors/mdm/devposture` and built once in `connectors/mdm/devrecord`). **Jamf** collects managed-Mac posture (FileVault disk-encryption, screen-lock/passcode compliance, OS version, managed/supervised/enrollment state, the device→owner assignment identity) via the read-only Jamf Pro API (`GET /api/v1/computers-inventory`, posture-relevant inventory sections only). **Intune** collects managed-device compliance posture (BitLocker disk-encryption, `complianceState`, OS version, management/enrollment state, the device→owner assignment identity) via the read-only Microsoft Graph device-management API (`GET /deviceManagement/managedDevices`, explicit posture `$select`). Each record is pushed to the platform's single `IngestEvidence` / `Push` API with a sha256 content-hash and stable optional fields — **no platform-side wire change** (invariant #3, P0-490-1); each registers `profiles_supported=[pull]` and names its interval honestly (operator-scheduled, recommended 24h — **not** "continuous monitoring", P0-490-6). **The load-bearing over-collection guard (P0-490-3 / threat-model I):** both connectors collect posture/compliance **summary + the device→owner ASSIGNMENT identity only** (opaque assigned-user id + optional display name) — and **never** device geolocation, the installed-app inventory (Jamf `APPLICATIONS` / Intune `detectedApps`), device contents, browsing data, or owner personal contact detail (phone / personal email / address). The guard is enforced **by construction** at three layers: the `devposture.RawDevice` + per-vendor raw types have no field for geolocation / apps / contact detail (a leak is a compile error); the vendor clients request ONLY the posture-relevant data at the API boundary (Jamf never requests `APPLICATIONS` or the GPS `location` section; Intune's `$select` never includes `detectedApps` / `phoneNumber` / `emailAddress`); and the record builder allow-lists payload keys. Tests: `TestEmittedRecords_NoGeoOrAppsOrPII` (both connectors) asserts only allow-listed keys + no over-collection substring reach a payload (AC-10), the client tests assert the request itself never asks for the excluded sections/props, and `TestCredential_NeverLogged` asserts the MDM credential is never logged (AC-11). **The load-bearing remote-wipe guard (P0-490-2 / threat-model E):** each connector requires a **read-only device-read credential only** — Jamf an API client bound to a read-only API role (Read Computers / Read Mobile Devices); Intune an Entra app granted only `DeviceManagementManagedDevices.Read.All` — surfaced by each `permissions` subcommand with an explicit warning that a write/management MDM credential is a **remote-wipe** risk and must never be used (the auth-package tests hold `RequiredRole`/`RequiredPermission` to read-only). Source credentials are read only from the environment (never a CLI flag), redacted on every credential format path, and never placed into a record (P0-490-4). Both are **OSS, in-tree, API-based** — the on-device agent is the customer's own MDM, not a security-atlas agent (P0-490-5, consistent with the osquery/Fleet/read-only-API posture) — and faked in tests (no live Jamf/Intune in CI — thin read-only HTTP clients handling the OAuth client_credentials token exchange + the bounded read; per-connector in-package bufconn integration tests exercise the full collect → build → `Push` → receipt round-trip + same-hour idempotency). The shared `endpoint.device_posture.v1` JSON Schema lands in the schema-registry tree with `x-default-scf-anchors=[END-04, CFG-02]` (Endpoint Security + Secure Baseline Configurations — consistent with `osquery.host_posture.v1`, flagged for maintainer recheck per OQ #9) and is registered in `DefaultSeed`; **no migration** (evidence flows through the existing ledger). v0 reads the first bounded page per MDM (bounded page size + run timeout — threat-model D). Software-inventory evidence, configuration-profile detail evidence, and an event-driven webhook profile are filed as follow-on slices 555–557 (P0-490-7). **Type: JUDGMENT** — the shared-vs-per-connector evidence-kind decision, the posture field set, the device→owner assignment-identity boundary, the `x-default-scf-anchors`, the scope minimums, and the per-MDM read-only auth scope recorded with confidence + detection-tier in `docs/audit-log/490-mdm-connectors-decisions.md`.
