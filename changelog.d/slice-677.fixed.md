- **fix(metrics): slice 677 — metrics correctness (freshness consistency, count labeling, neutral no-target badge) (closes 677).** Three metric-display correctness defects re-verified on `main` build `2a3805b` in the demo tenant, bundled because they share the metrics surface. **(ATLAS-020, high)** The dashboard freshness widget read **100% within window** while the Metrics view read **Evidence freshness = 0.0%** for the same tenant. **Root cause:** both surfaces ultimately derive from the same `evidence_freshness` read model (one row per (tenant, control)), but the dashboard read it **live** (`GET /v1/evidence/freshness`) while the metrics view rendered the **latest stored metric observation** — a point-in-time 0.0% snapshot captured by the metrics scheduler **before** slice 671 wired seed-evaluation to populate the read model. The fix removes the second read path: a new single-source-of-truth helper `web/lib/api/freshness-consistency.ts` (`freshnessPctFromReport`) is the **one** definition both surfaces use — the dashboard subtitle's `computeFreshnessPct` delegates to it, and the metrics board KPI card (`web/components/dashboards-metrics/board-metric-card.tsx`) reads the **live** `FreshnessReport` (sharing the dashboard's TanStack query key) for its headline value + badge, so the two surfaces **cannot** disagree by construction. The stored-observation series still backs the trend sparkline. **(ATLAS-021, medium)** The dashboard freshness widget counted over **50** ("0 of 50") while the evidence ledger reported **200** ("Showing 50 of 200"), reading as a 4× contradiction. They count genuinely different populations — the freshness widget counts **controls** (latest-per-control verdicts), the ledger counts all append-only evidence **records** (invariant #2). This is a **labeling** fix: the freshness panel (`web/components/dashboard/evidence-freshness-panel.tsx`) now labels its unit as "controls" ("{n} of {total} controls have their latest evidence past its freshness window. (Controls, not ledger records — the evidence ledger counts every append-only record.)") so the two no longer read as a discrepancy. **(ATLAS-023, medium)** A metric with value 0.0% / 0 and "no target set" rendered a green **"on target"** pill — actively misleading on a board surface read at face value. **JUDGMENT D1:** `thresholdBadgeColor` (`web/lib/api/metrics.ts`) now returns **`neutral`** (not green) when there is no target row or no `target_value`; green is reserved exclusively for value-meets-target. **D2:** the two neutral cases are disambiguated by copy via a new pure `neutralBadgeLabel` helper — no observation → "no data", value-but-no-target → "no target" — both the same muted badge, never green. **AC-4 proof:** vitest pins the badge branches (`web/lib/api/metrics.test.ts`, no-target → neutral; zero-value → neutral; `neutralBadgeLabel` cases) and the shared freshness definition (`web/lib/api/freshness-consistency.test.ts`, including a `test.each` asserting the dashboard `computeFreshnessPct` equals `freshnessPctFromReport` for every input — the consistency contract), with a per-file coverage floor added same-PR; Playwright `web/e2e/metrics-correctness-consistency.spec.ts` (hermetic, route-mocked BFF per slice 594 — no seed-harness dependency) serves one fixed `FreshnessReport` to both surfaces and asserts the freshness % is **identical** on the dashboard widget and the metrics KPI, the freshness panel labels its population as "controls", and a no-target board metric renders a **neutral** badge ("no target"), never green. **Anti-criteria honored:** does **not** change the evidence ledger or the freshness-window definition (display + consistency + badge semantics only — `git diff --stat origin/main...HEAD -- internal/ migrations/ proto/ cmd/` is empty), and never shows green for a genuinely-unmet or no-target metric. **Type: JUDGMENT.** Decisions log: `docs/audit-log/677-metrics-correctness-decisions.md`.
