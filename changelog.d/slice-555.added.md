- **feat(connectors): slice 555 — MDM software-inventory evidence (Jamf + Intune).** Slice 490 shipped the Jamf + Intune MDM connectors with a single posture-summary kind (`endpoint.device_posture.v1`) and **deliberately excluded the installed-application inventory** (Jamf `APPLICATIONS` section / Intune `detectedApps`) as the load-bearing over-collection guard (P0-490-3): a full app inventory is high-volume, PII-adjacent data the posture-summary control question does not need. This slice adds that inventory back as a **separate, scoped** evidence kind `endpoint.software_inventory.v1`, emitted by the SAME two connectors via the SAME locked pattern, because it answers a **different** control question — patch-/vulnerability-management and asset inventory ("are managed endpoints running patched, authorized software?"), `x-default-scf-anchors = [VPM-04, AST-03]`. **The load-bearing guard (P0-555 / threat-model I): each software item carries the app NAME + optional VERSION + optional bundle/package IDENTIFIER + optional INSTALL DATE only — NEVER file paths, per-user app-usage telemetry, license keys, device contents, browsing data, or owner personal contact detail.** Enforcement is structural at three layers (the slice-490 gold standard): (1) the shared `swinventory.SoftwareItem` + the per-vendor `RawSoftwareItem` Go types have NO field for a path / usage / license key — a leak would be a compile error; (2) the vendor clients request ONLY the software-relevant data at the API boundary — Jamf asks for the `GENERAL + APPLICATIONS` inventory sections (never `USER_AND_LOCATION` / GPS `location`), Intune `$select`s `id,displayName,version` on `detectedApps` with `managedDevices($select=id)` (never `sizeInByte`, `deviceName`, or `userPrincipalName`), both read-only GETs; (3) the record builder allow-lists every payload + per-item key. A new shared `connectors/mdm/{swinventory,swrecord}` package family mirrors the slice-490 `{devposture,devrecord}` split (one normalizer + one record builder across both vendors), the `idem` package gains a kind-namespaced `SoftwareInventoryKey` (so a device's posture record and its software record never collide on the same key for a given device+hour), and each connector gains a `run-software` subcommand (pull profile; honest 24h operator-scheduled cadence — NOT continuous monitoring). The per-device software list is stable-sorted and bounded (`MaxSoftwarePerDevice = 500`, a defensive over-collection ceiling). Read-only credential is **identical** to `run` (no new MDM scope; no write/management permission — the remote-wipe guard from slice 490 is unchanged); records are `service` + required `--environment` scoped; `Result = INCONCLUSIVE` (the platform evaluator owns known-vulnerable-version detection). Wired into `schemaregistry.DefaultSeed()` + the bundled JSON Schema (`endpoint.software_inventory/1.0.0.json`); the slice-068 schema-drift bijection passes. New floored packages `connectors/mdm/swinventory` (94) + `connectors/mdm/swrecord` (91). No migration — evidence flows through the slice-013 ledger. The over-collection guard is proven by `TestBuild_PayloadAndItemsCarrySoftwareFieldsOnly` (allow-listed keys + banned-substring assertion) plus per-connector client tests asserting the request never asks for the banned sections/props. **Type: JUDGMENT** — the separate-sibling-kind-vs-posture-extension call, the per-device-roll-up-vs-per-app-record shape, the software-field allow-list, the SCF anchors, and the over-collection-exclusion boundary recorded with detection-tier in `docs/audit-log/555-mdm-software-inventory-decisions.md`.
