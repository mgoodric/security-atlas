- **feat(catalog): slice 482 — per-requirement coverage-strength rollup + confidence-band visualization (the canvas §3.2 headline promise).** Canvas §3.2 promises the platform can compute _coverage strength_ per requirement through the STRM-edge `strength` field ("if your evidence covers SCF:IAC-22 with strength 1.0, and ISO27001:A.9.4.2 → SCF:IAC-22 with strength 0.8, the ISO requirement is covered at 0.8, and the UI surfaces the gap"). The raw ingredients existed — slice 438's per-edge `strength`, slice 012's control-state evaluation, slice 016's freshness, and the `GET /v1/requirements/{id}/coverage` endpoint that already returns each anchor's `strength` — but the rollup and its visualization did not; slice 438 (P0-438-6) and slice 447 explicitly deferred coverage-strength visualization to this follow-on (roadmap §10.2). **(1) Backend read-model (AC-1/AC-2/AC-3):** `GET /v1/requirements/{id}/coverage` gains two **additive** fields — `coverage_strength` (numeric 0.0–1.0) + `confidence_band` (string) — computed **server-side** (no client-supplied strength — P0-482-4) from each anchor's edge `strength` combined with the tenant's evaluated coverage state. The formula (the JUDGMENT call) is **best-satisfying-path**: `coverage_strength = MAX over anchors of (edge_strength × anchor_coverage)`, where `anchor_coverage` is the best 30-day effectiveness pass rate over the tenant's RLS-scoped controls on that anchor, gated by FrameworkScope — the same per-control number slice 256 ships on `/v1/controls/{id}/coverage`, aggregated requirement-side. The single-anchor case reduces **exactly** to the canvas worked example (0.8 × 1.0 = 0.8 → "strong"). The existing `requirement` / `anchors` / `controls` payload fields are **unchanged** (additive only — P0-482-5); the per-anchor `strength` stays (AC-3). **(2) The load-bearing RLS isolation (threat-model I / P0-482-3 / invariant #6):** because the rollup folds in the tenant's evaluated state, `coverage_strength` is **tenant-confidential derived data**, not global catalog data — it is computed **only** over the RLS-scoped `controls` rows (the same scope the existing `controls[]` array uses, no `WHERE tenant_id` clause; RLS does the filtering at the DB layer). A requirement the tenant has no controls for resolves to the **uncovered** band (empty, never a foreign tenant's value); a control whose framework is out of FrameworkScope, or that has no effectiveness data, contributes nothing (the slice-256 null contract, lifted to the rollup). An integration test (AC-7) seeds a **strong** (0.8) control for tenant A and proves tenant B sees `0` / `uncovered` for the same requirement — never tenant A's score. **(3) Confidence bands (the JUDGMENT call):** four bands with cut points pattern-matched to the canvas example — `strong` [0.80, 1.0] (0.8 is the floor — the canvas value reads as strongly, not perfectly, covered, with the 0.2 gap shown alongside), `partial` [0.50, 0.80), `weak` (0, 0.50), and `uncovered` (no in-scope evaluated path). A genuine 0.0 score _with_ an in-scope control (0% pass rate) classifies as **weak**, not **uncovered** — "covered but failing" is a real state distinct from "no coverage" (slice 256 P0-256-1, carried up). **(4) Freshness weighting (decisions-log call):** **not** folded in for v1 — the 30-day effectiveness window is already freshness-bounded, so re-applying slice-016 freshness would double-count; a distinct freshness _penalty_ is a deliberate v2 enrichment on the revisit list. **(5) UI (AC-4/AC-5):** the control detail view's coverage table (`web/components/control/coverage-table.tsx`) gains a **Confidence** column — one band badge per requirement row derived from the per-row coverage with thresholds mirroring the backend (`web/components/control/confidence-band.ts`, a styled badge — no new charting dependency), carrying `data-band` for value-driven assertions; the footer documents the thresholds. A new requirements-coverage **BFF route** (`web/app/api/requirements/[id]/coverage/route.ts`, httpOnly-bearer pass-through, no client-supplied input) + lib type (`web/lib/api/requirement-coverage.ts`) carry the additive fields for a future requirement-detail page. **Scope discipline (P0s):** read + visualize **only** — does NOT ship the crosswalk-review/conflict editing UI (P0-482-1, separate slice), does NOT change how `strength` is stored or how the 438 loader writes edges (P0-482-2), and does NOT add a cross-framework comparison matrix (P0-482-6) — both filed as follow-on docs slices 536 + 537. **Tests:** fast pure-Go unit branches for the formula + band thresholds (`helpers_test.go`, no DB — AC-8, slice-353 Q-2) run on every CI run; integration tests (AC-6 mixed-strength edges + mixed evidence → expected band; AC-7 the RLS cross-tenant isolation proof) run on the already-enrolled `internal/api/ucfcoverage` shard; vitest covers the band classifier + the BFF mapping; a Playwright assertion (commented per the slice-082 seed-harness convention) covers the band rendering. New web per-file coverage floors added per the slice-347 ratchet; raises the `internal/api/ucfcoverage` Go floor's headroom (no migration — reads existing edges + state). **Type: JUDGMENT** — the rollup formula, the no-freshness-weighting choice, and the band thresholds + labels recorded with confidence + detection-tier in `docs/audit-log/482-coverage-strength-rollup-decisions.md`.
