- **fix(pdf): slice 475 — the board + questionnaire PDF endpoints now degrade DETERMINISTICALLY to 503 under a slow/contended/absent headless chrome, never a 500 or a hung request.** The PDF endpoints render via headless chromium (chromedp). Under sustained CI load the render previously neither completed (200) within its deadline nor degraded cleanly to 503: a deadline-exceeded chromedp error fell through the handler's `ErrChromeUnavailable` check and surfaced as a **500** (the handler's `httperr.WriteInternal` default branch) or, worse, a request that hung past the client deadline. The board integration test `TestPDF_ReturnsPDFOrServiceUnavailable` and the questionnaires twin `TestExportPDF_SmokeTest` (both written to accept 200-or-503 and fail on anything else) flaked at ~30.1s across batches 193/195/196 and then failed two consecutive reruns blocking batch 197. **Fix:** a new process-wide governor `internal/pdfrender.Limiter` now fronts BOTH renderers (`board.RenderPDF` / `board.RenderPackPDF` / `questionnaire.RenderPDF` route through `pdfrender.Default().Do`). It (1) bounds the render with a tunable deadline raised from 30s → **90s** default (env `ATLAS_PDF_RENDER_TIMEOUT`) so a healthy render completes with generous headroom while still bounding a hang (AC-2); (2) caps **total** concurrent chrome renders at **2** (env `ATLAS_PDF_RENDER_MAX_CONCURRENCY`) across both packages — chrome is one OS-level resource, so the limiter is shared, not per-package — with a bounded **15s** wait (env `ATLAS_PDF_RENDER_QUEUE_WAIT`) before an over-cap caller degrades (AC-3); (3) classifies a deadline by the RENDER CONTEXT (not by sniffing chromedp's error text) into `ErrRenderDeadline`, and a saturated queue into `ErrQueueSaturated`. The handlers map `ErrChromeUnavailable` / `ErrRenderDeadline` / `ErrQueueSaturated` ALL to **503** (the documented graceful path) and emit a WARN distinguishing `chrome_absent` / `render_deadline_exceeded` / `render_queue_saturated` (AC-5); a genuine bug still 500s. **No change to PDF content/templates**, the `chromedp` dependency, or the slice 340/341 `WSURLReadTimeout` connection-setup fix (this is complementary RENDER-TIME degradation) (AC-6). **Proof:** both integration tests are now deterministic 200-or-503 (no `t.Skip` on 503) and gain a render-deadline→503 test (1ns render deadline → 503, proving the deadline-exceeded path no longer 500s), a queue-saturation→503 test, and an N× stress variant under simulated contention (slice-340 pattern) — all green 5× with `-race`; the `pdfrender.Limiter` unit suite (deterministic deadline / saturation / concurrency-cap-honored / parent-cancel / fail-fast / env-parsing) is green 20× with `-race`. **Type: JUDGMENT.** Decisions log: `docs/audit-log/475-pdf-render-degradation-decisions.md`.
