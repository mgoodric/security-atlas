- **feat(catalog)!: an SCF release is required on every write that binds an SCF code (#1774).** **BREAKING.** Nothing that writes binds an SCF code in "whatever release is current" any more. The SCF reuses codes between releases, so that could anchor a control or edge to a different control's meaning. Each path below now fails, writes nothing, and its error gives the one-line fix:
  - **Control bundle upload:** a `control.yaml` whose `scf_anchor_id` is a code needs `scf_release: <release>`, e.g. `scf_release: test-2026.3`. The response is 400. An anchor UUID or an unanchored bundle (`anchor_fit: none`) needs no release. `atlas-cli controls validate <dir>` now fails and lists every bundle missing the field in one run.
  - **Crosswalk import:** a YAML crosswalk needs a top-level `scf_release: "<release>"`. A workbook whose `SCF <release>` sheet names a release that is not loaded is now refused instead of binding in the current release. The usual fix is to load that release first: `atlas-cli catalog import-scf <same .xlsx>`, then import the crosswalk again. To import a workbook into a different loaded release, rename its sheet to `SCF <release>`, or rewrite it as YAML that declares `scf_release`. There is no workbook-to-YAML converter, and a sheet name cannot spell a `test-` label such as `test-2026.3`.
  - **OSCAL component, catalog and profile imports (`atlas-oscal`):** pass `--scf-release <release>` or add an `scf-release` prop to the document's metadata. The import is refused before the document is sent for validation.
  - **Vendor-claim mapping (`PATCH /v1/oscal/component-claims/{id}/scf-anchor`):** send `scf_release` with `scf_anchor_id`. The response is 422 without it. `GET /v1/anchors` now reports the `scf_release` its anchors are in, and the web UI sends it.
  - **Mapping overlay edges (`POST /v1/mapping-overlays` and bulk import):** `scf_release` is required. The response is 400 `invalid_overlay_edge` without it, and a CSV import whose header has no `scf_release` column is refused. `atlas-cli mappings overlay add` requires `--scf-release`.
  - **Stock policy seed (`atlas-cli policy seed-stock`):** a policy that links SCF codes needs `scf_release` in its frontmatter, and the release must be loaded. The shipped policies already declare `test-2026.3`.
  - **Demo seed:** it adopts anchors only from `test-2026.3`, the bootstrap sample. When that release is not loaded, the demo seed synthesizes its own anchors.

  **Unchanged on purpose:** two staged paths still take the release that is current when they read it, record it, and bind only in that recorded release, never in whatever is current at approval.
  - The **AI question-mapping suggestion** (`POST …/scf-mapping/ai-suggest` without `?scf_release=`) records the release on its proposal and returns it. Approval copies the recorded code.
  - **Control-import staging** records the current release on the batch. The batch response returns it as `scf_release`, and the review page shows it. Approval binds every row in that release.

  **Upgrade note:** boot is unaffected. Bootstrap uploads only the shipped stock bundles, crosswalks and policies, and all of them declare `scf_release`. Controls already stored without `scf_release` keep their anchors and keep working. Only re-uploading such a bundle fails, until its `control.yaml` declares the release. Run `atlas-cli controls validate <dir>` over your bundles to find them. Read endpoints still default to the current release and say which release they used.
