- **feat(notify): slice 582 — notification-channel digest scheduler (fan-out driver).** Slices 445 (email) and 543 (Slack/webhook) each shipped the delivery SUBSTRATE — a per-user opt-in + a `DeliverDigest(ctx, userID, recipientUserID)` primitive that builds, claims, and delivers ONE user's minimum-disclosure digest — but neither shipped the DRIVER that walks all opted-in users on a schedule and calls `DeliverDigest` for each; the primitives were invoked only by tests. This slice adds that recurring driver: a new `internal/notify/scheduler` package — an **in-process daily tick-loop** (mirroring the slice-076 metrics + slice-510 backup schedulers — **no external cron** for the single-VM self-host target; `DefaultInterval` `24h`, overridable via `ATLAS_DIGEST_INTERVAL`) wired into `cmd/atlas/main.go` startup. **(1) Enumeration (D2):** three new sqlc queries (`ListEmailOptInUsers` / `ListSlackOptInUsers` / `ListWebhookOptInUsers`, each `SELECT tenant_id, user_id ... WHERE enabled = true`) run through the migrator (BYPASSRLS) pool — the ONE deliberate cross-tenant read, returning ONLY the `(tenant, user)` keys (no notification content, no PII). `enabled = false` / no-row are excluded by the `WHERE`, so **default opted-OUT** (P0-445-7 / P0-543-3) is honored at the SQL layer. **(2) Tenant isolation (canvas invariant #6):** each per-user delivery runs the EXISTING `DeliverDigest` under that user's OWN tenant context (`tenancy.WithTenant`), so every read inside the sink is RLS-scoped — Tenant A's notifications can never reach Tenant B's user (proven by `TestSweepOnce_TwoTenantsNoCross`). The slice-029 `recipient_user_id` passed is the user's UUID string, the contract the sinks already use. **(3) Idempotency (D3):** the driver adds NO new idempotency surface — it reuses each sink's claim-before-send (the per-UTC-day `digest_key` UNIQUE), so a second sweep the same day double-CALLS `DeliverDigest` but does NOT double-SEND (`TestSweepOnce_IdempotentNoDoubleSend`). **(4) Scope discipline (P0):** a delivery driver, NOT a producer — it reads the opt-in tables and drives the existing minimum-disclosure builders unchanged; it never writes a notification and never widens per-channel disclosure. Per-user + per-channel **try/log/continue** — one failing delivery or a channel enumeration error does not abort the sweep for the rest. The driver depends on a 1-method `DigestDeliverer` interface + an `OptInLister` func; thin per-channel adapters (`channels.go`) bind email/slack/webhook without the driver importing each `DeliveryResult` type. **(5) main.go mounting (D5):** only channels whose config is present are mounted (email when SMTP configured, Slack/webhook when a URL is set + passes the startup SSRF guard); no configured channel → scheduler not started. **Honest-interval discipline:** the digest period is named explicitly (per-UTC-day / daily), NOT marketed as "continuous monitoring". **No migration** — the existing slice-445/543 opt-in tables suffice. New floored package `internal/notify/scheduler` (floor 69, merged unit+integration 71.43%) + integration-shard enrolment (leg B2). **Type: JUDGMENT** — scheduling shape, enumeration mechanism, idempotency reuse, and channel-binding recorded with detection-tier in `docs/audit-log/582-digest-scheduler-decisions.md`.
