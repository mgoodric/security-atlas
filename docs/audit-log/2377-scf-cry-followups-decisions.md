The changelog fragment is `changed` and carries an **Upgrade note**, listing each connector default's old and new code. ## D3 — Own-words pass: every sample description is rewritten

The rule is in the sample's own header. Titles and IDs are SCF's, used unmodified under CC BY-ND 4.0; descriptions are claimed to be "security-atlas's own wording, not SCF text". The project does not bundle SCF content beyond IDs and titles (OQ #1, and the `scf-pin.json` comment).

I checked the 93 sample descriptions against the "SCF Control Description" column of the pinned 2026.3 workbook (sha256 `5a89bf2d…a7df697`, the same file `scf-pin.json` pins). The check used a `difflib` ratio and was run locally; the workbook is not committed.

- Five rows matched SCF 2026.3 text exactly: `THR-06`, `THR-11`, `THR-13`, `THR-15`, `THR-16`.
- Five more scored 0.88 to 0.95: `MON-02`, `THR-04`, `CPL-02`, `TPM-02`, `IRO-08`.
- Many low scorers were verbatim SCF text from earlier releases. For example, `IAC-01`'s "Mechanisms exist to facilitate the implementation of identification and access management controls" is the older SCF `IAC-01` wording. A low score against 2026.3 did not show the text was ours.
- All 93 used SCF's "(Cryptographic) Mechanisms exist to …" form.

Rewriting only the high scorers would have left text that is SCF's in another release, and would have left the header's claim false. So all 93 descriptions are rewritten in plain declarative sentences that say what the organization does, without the SCF form. Afterwards no row scores above 0.67 against 2026.3. The highest scores come from shared domain terms that are also in the titles ("indicators of compromise", "insider threat").

Wording constraints held while rewriting:

- `CRY-07` and `CRY-05` still contain "encryption" (#1976: a search for it must still find both rows), and now say "at rest" and "in transit" in the description too.
- No row claims more than its title. A description is a short gloss of the control's intent, not a requirement.
- Titles and IDs are not touched; the pin guard (`scfpin_test.go`) still passes.

## D4 — The open `test-2026.3` label absorbs the change

Changing descriptions changes the sample's anchor content, so `TestSampleFixtureContentIsPinnedToItsRelease` failed as expected. `test-2026.3` has not shipped in a tag (`git tag --contains 8bad7757` is empty), so it is still the open working label from 1971 D2. Its pinned hash is updated in place, as every #1717 family group did, instead of minting a new label. The cost is the one 1971 D2 names: a development install that already imported an earlier `test-2026.3` state fails its next bootstrap with `ReleaseConflictError` and needs a catalog reset (a fresh database, or `just scratch-pg-up`). No shipped install has imported `test-2026.3`.

The ticket's brief said not to touch real catalog data files or migrations. `scf-sample.json` sits under `migrations/fixtures/` but is our own sample, and its descriptions are what the own-words pass covers. No `migrations/sql/` file and no real SCF data file (`scf-pin.json`) changed.
