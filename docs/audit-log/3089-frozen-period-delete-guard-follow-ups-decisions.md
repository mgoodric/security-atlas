# #3089 — frozen-period delete guard follow-ups: build-time decisions log

detection_tier_actual: manual_review
detection_tier_target: integration

Non-blocking findings from the #3088 review (#3081) and the #3090 review (#3085). The lock-level error was in comments and docs only, so no behaviour was wrong, but nothing measured the lock. `TestOwnerDelete_LockLevel` now does: it reads `pg_locks` after `period.OwnerDelete` and finds `ShareRowExclusiveLock`, still held after the trigger is enabled again. The same measurement by hand on a migrated scratch database, in one transaction:

```
ALTER TABLE audit_periods DISABLE TRIGGER audit_periods_frozen_no_delete_trg;  -> after disable: ShareRowExclusiveLock
ALTER TABLE audit_periods ENABLE TRIGGER audit_periods_frozen_no_delete_trg;   -> after enable: ShareRowExclusiveLock
```

## Decisions

| #   | Decision                                                                                                                                                                                                                                            | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | One exported helper, `period.OwnerDelete`, and one constant, `period.FrozenNoDeleteTrigger`, in `internal/audit/period`. `demoseed.execTeardownDelete` and `dbtest.DeleteAuditPeriods` both call it.                                                | The period package owns the table and its guards. `demoseed` (production) cannot import `dbtest` (integration-only build tag), so the helper has to live in a production package. `go vet -tags=integration ./internal/...` shows no import cycle.                                                                                                                                                                                                                                                                                                                 |
| D2  | The demo teardown passes a 2s lock timeout; `dbtest.DeleteAuditPeriods` passes none.                                                                                                                                                                | On a live install a teardown that waits for the lock queues every tenant's `audit_periods` writes behind its pending ALTER. Failing with `lock_not_available` (55P03) lets the operator retry. A test cleanup on a CI database has no such cost, and a timeout there would turn lock contention between parallel suites into flakes, which the integration tier does not retry.                                                                                                                                                                                    |
| D3  | The timeout is set with `set_config(..., true)` for the ALTER only, and the session's previous `lock_timeout` is restored once the lock is held.                                                                                                    | `SET LOCAL` would last for the rest of the teardown transaction and apply to statements that have nothing to do with this lock.                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| D4  | `audit_periods` moves in `teardownTables` from after `audit_period_audit_log` to just before `framework_versions`.                                                                                                                                  | Its only foreign-key parent is `framework_versions` (RESTRICT). Its children the seed writes (`populations`, `walkthroughs`) are already swept earlier, and no table between the old and new position references it (checked against `pg_constraint`). The lock is held until commit, so taking it later keeps the hold shorter.                                                                                                                                                                                                                                   |
| D5  | The unbound-rows purge now reports `RetainedDeleteTrigger` for a table whose only retain signal is a `BEFORE DELETE` row trigger. The SQL returns a kind (`ledger`, `delete_trigger`, or empty), and an unrecognised kind maps to `RetainedLedger`. | `audit_periods` is not an append-only ledger. `atlas_app` may delete open periods from it. Only `audit_periods` gets the new reason on the current schema. The behaviour is unchanged (#3081 D5); `TestPurgeUnboundRows_KeepsAuditPeriods` pins it, with an open period that the purge keeps.                                                                                                                                                                                                                                                                      |
| D6  | Migration `20261315000000` revokes PUBLIC EXECUTE on `audit_periods_frozen_has_controls()`.                                                                                                                                                         | It is SECURITY DEFINER. Firing a trigger does not check EXECUTE, so the deferred check still runs for `atlas_app`: the period suite's app-role freezes pass with the revoke applied. `TestFrozenControls_CommitCheckNotPublic` failed with the down file applied (`atlas_app EXECUTE ... = true, want false`) and passes with the migration re-applied.                                                                                                                                                                                                            |
| D7  | The role-switch test now checks the message `reserved for the migration and the seed` as well as SQLSTATE 23514.                                                                                                                                    | The same insert guard raises 23514 on its not-frozen branch too, so a code-only check could pass on the wrong branch.                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| D8  | The optional `BEFORE TRUNCATE` trigger on `audit_periods` is not added.                                                                                                                                                                             | `internal/platform/status_integration_test.go` runs `TRUNCATE tenants, users ... CASCADE`, which reaches `audit_periods` through `frameworks` and `framework_versions`. A refusing trigger would fail that suite whenever a frozen period is in the shared CI database. Only the owner may TRUNCATE, and only on purpose. It is the same gap #3050's triggers leave, and closing it for both tables belongs in its own ticket. That ticket is #3094, which also corrects the cascade path: see `docs/audit-log/3094-frozen-period-truncate-guard-decisions.md` D1. |
