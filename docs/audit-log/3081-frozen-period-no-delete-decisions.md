# #3081 — a frozen audit period cannot be deleted: build-time decisions log

detection_tier_actual: manual_review
detection_tier_target: integration

Found in the #3077 review (#3066). `atlas_app` holds DELETE on `audit_periods` under the `tenant_delete` RLS policy, and #3062's immutability trigger guards UPDATE only, so the app could delete a frozen period that had no `ON DELETE RESTRICT` children. That erased its `frozen_hash` and cascaded away its recorded control set. No product code deletes a period, and no test tried it. `TestFrozenPeriod_DeleteRefused` now does. With migration `20261313000000` reverted (its down file applied to the test database), it fails with `app delete of a frozen period: want check_violation (23514), got <nil>`. With the migration re-applied it passes.

Matt decided on 2026-11-24 to block this. The dispatcher relayed a preference for a trigger over a revoke.

## Decisions

| #   | Decision                                                                                                                                                                                                                       | Why                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | A `BEFORE DELETE` row trigger, `audit_periods_frozen_no_delete_trg`, refuses `status = 'frozen'` for every role. `atlas_app` keeps its DELETE grant.                                                                           | A revoke closes only the app's path. The owner and every BYPASSRLS role could still delete a frozen period with a stray statement. #3050 already made the original freeze immutable for every role, with owner recovery disabling the trigger in its own transaction, so this follows the same rule. An open period stays deletable, which costs nothing and keeps a future "discard a draft period" verb possible.                                                              |
| D2  | `audit_period_frozen_controls` keeps `ON DELETE CASCADE`, not `RESTRICT`.                                                                                                                                                      | Frozen deletes are now refused, so the cascade runs only when the owner has disabled the trigger to tear a period down, and removing the snapshot with its period is what that teardown wants. An open period has no snapshot (the insert guard requires a frozen period, and a reopen removes it). RESTRICT would add no protection beyond the trigger, and would make each teardown disable a second trigger and delete the snapshot by hand. #3066 D3 had made the same call. |
| D3  | Owner teardown disables the trigger around its own `audit_periods` DELETE only: `demoseed.execTeardownDelete` for the demo teardowns (whole-tenant, in-place, legacy) and `dbtest.DeleteAuditPeriods` for test cleanups.       | `ALTER TABLE ... DISABLE TRIGGER` is transactional, so no other session sees the trigger disabled, and a failed DELETE rolls the disable back with its transaction or savepoint. Wrapping only the one DELETE keeps the `ACCESS EXCLUSIVE` lock off the other teardown statements. An in-trigger exemption for BYPASSRLS roles was rejected: it would let the owner delete a frozen period by accident, which is what D1 rules out.                                              |
| D4  | Test cleanups that delete frozen periods were moved to `dbtest.DeleteAuditPeriods`. Cleanups in suites that never freeze a period were left alone.                                                                             | Those suites never hit the trigger, and routing every cleanup through an `ACCESS EXCLUSIVE` lock would serialise suites that run in parallel within a package. Cleanup errors in these suites are only logged, so a missed site would leave rows behind rather than fail. The integration run was checked for the trigger's message in cleanup logs (none).                                                                                                                      |
| D5  | The unbound-rows purge (`internal/auth/oauthclient`) is not changed. It treats any `BEFORE DELETE` row trigger as an append-only signal, so it now retains all-zeros-tenant `audit_periods` rows, and the rows they reference. | That fails closed: an audit period in the all-zeros tenant is kept and listed with a reason, not deleted. Teaching the purge to delete open periods only would add a second special case for a tenant that should hold none.                                                                                                                                                                                                                                                     |
| D6  | `internal/api/adminauditlog/export_integration_test.go` keeps its cleanup through `appPool` with no tenant GUC.                                                                                                                | That cleanup already deletes nothing (RLS denies on missing context), before and after this change. Fixing it is outside this ticket.                                                                                                                                                                                                                                                                                                                                            |
